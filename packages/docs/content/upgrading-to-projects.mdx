---
title: Upgrading to projects
description: What changes when a server moves from pods to projects, and what to do before and after.
---

The release that brings projects replaces pods, routines, sandboxes and
artifacts with projects, automations, computers and files. It's the largest
update so far, so plan for it.

## Before you start

- **Back up first.** See [Backups](/docs/deploy-with-docker#backups). The
  upgrade can't be undone except by restoring a backup.
- **Plan for downtime.** Stop every copy of the old version, then start one
  copy of the new version to run the migration. Wait until it is ready, including
  the file moves at startup, before starting other replicas. Time the SQL and
  startup on a restored production snapshot to size the window. Leave room for
  PostgreSQL's write-ahead log (WAL). An upgrade with about one million messages
  generated about 3 GiB of WAL.
- **Check whether the migration committed before restarting the old version.**
  Restart it only after confirming that the SQL transaction rolled back. If the
  upgrade fails after commit, continue with the new version or restore the
  matching database and blob store backup.
- **Know what migrates the database.** The Docker image migrates it by
  default, as the new version first starts. Set `SUGABOTS_SKIP_MIGRATIONS` to
  `true` (see [Configuration](/docs/configuration)) to have the image skip
  that, and migrate it yourself. A server run from source never migrates its
  database on its own: run `bun run db:migrate` before you start the new
  version.

## What changes

- **Shared pods become private projects** with the same members. Each bot of
  a shared pod becomes a private bot whose members are exactly the pod's
  members, and stays in the project. Its own chats, files, connectors and
  automations stay with the bot. A creator who was outside the pod at the time
  of the upgrade stays outside the bot and cannot manage it. The workspace's
  owner or an admin can add them back.
- **Each project has a lead bot that answers its chats.** In a pod's chats,
  bots only answered when someone mentioned them or replied to them. Now a
  message that mentions no bot and replies to none goes to the project's lead
  bot. The first bot created in a shared pod becomes its project's lead.
  Projects from pods with no bots share a new lead bot per workspace. It has
  no model, so it answers only after an owner or admin gives it one. They can
  also choose a different lead in each project's settings.
- **Pod members can run its bots' automations by hand.** A shared pod's
  members become members of its bots, and anyone who reaches a bot, but a
  viewer, may start its automations by hand, paused ones included. Before,
  only owners and admins could.
- **Admins see which personal bots there are.** Each member's personal bots,
  such as their Personal Assistant and the bots of their personal pod, show in
  owners' and admins' lists of bots. Admins still can't talk to them or read
  their chats and files.
- **Each bot gets its own connectors.** A pod's connectors are copied to each
  of its bots. The upgrade turns on the shared pod's bots' own connectors in
  the project the pod becomes. A shared pod with no bots keeps its connectors
  in that project. Sign-ins can't be shared between copies, so **every OAuth
  connector has to sign in again**: once for each bot it was copied to, and
  once in each project that kept one. Connectors that use an API key or no
  sign-in keep working.
- **A pod's GitHub app goes to one bot**: the oldest bot with automations
  started by it, or otherwise the pod's oldest bot, but never a Personal
  Assistant. A GitHub app can't be copied, so the pod's other bots'
  automations that GitHub started are **paused**. To start them again, set up
  a GitHub app for each of those bots, point the trigger at it, and resume
  the automation. A personal pod whose only bot is its Personal Assistant
  **loses its GitHub app**.
- **A personal pod with no bots loses its computer and connectors.** Its
  computer is destroyed at its provider, with everything on it, and its
  connectors are deleted. Its files are kept (see below).
- **Webhook triggers that only kept a digest of their secret are paused.**
  Older versions stored only a digest of some webhook secrets, which can't be
  used to check calls any more. Each such trigger refuses every call, and its
  automation is paused, until someone gives the trigger a new secret and
  resumes it. Update the secret wherever the webhook is sent from too.
- **Direct messages between members are deleted**, with their files. Members
  now talk in projects' chats.
- **Chat summaries are deleted.** Bots no longer summarise chats. What they
  cost still shows in usage.
- **Collaboration chats are removed.** A helper bot now answers in the chat
  it was asked from, so each collaboration chat's messages move into that
  chat, among its own messages in time order.
- **Work under way is stopped.** Every bot reply that was running or waiting
  for approval is cancelled, and every automation run under way is recorded as
  failed. Send the message again, or run the automation again, once the
  upgrade is done.
- **A Personal Assistant's automations are paused**, until the member it
  works for resumes them.
- **Reconnecting clients refetch the app's data.** The event history they
  usually catch up from is cleared during the upgrade.

## What keeps working

- **Old webhook addresses.** Webhooks sent to the addresses older versions
  gave out, under `/api/hooks/`, still reach their triggers and GitHub apps.
  So do the setup addresses each GitHub app was made with. You don't need to
  change them where they're configured.
- **Files and computers.** Files outside direct messages keep their contents.
  A shared pod's computer stays with the project it becomes. A personal pod's
  computer goes to its oldest bot other than a Personal Assistant, or to the
  Personal Assistant if it is the only bot. A personal pod with no bots gives
  its files to a new Personal Assistant for its owner, with no model until they
  choose one. Only they can see those files. Files kept on disk move to their
  new folders when the server starts.
- **Old docs links.** Links to renamed docs pages, such as `/docs/pods`,
  redirect to the page that replaced them.
