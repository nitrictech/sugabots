---
title: Connections
description: Plug apps like Linear and Notion into a pod, so its bots can work with them.
---

A connection links a pod to an app through the
[Model Context Protocol](https://modelcontextprotocol.io) (MCP). Once it's
connected, every bot in the pod can use the app's tools, with the
[approval](/docs/tools-and-approvals#tools-from-connections) you choose.

Admins add and manage connections. Members and viewers can see which ones a pod
has.

## Add one

Open the pod's settings, find **Connections**, and choose **Add connection**.

### Apps that sign in with one click

Pick one, choose its approval, then **Connect** and sign in to the app.

| App | What bots can reach |
| --- | --- |
| Linear | Issues, projects and cycles |
| Stripe | Customers, payments and invoices |
| Notion | Pages and databases |
| Sentry | Errors and performance issues |
| Jira | Issues and boards |

### Any other MCP server

Choose **Something else**, then **Connect by URL**, and fill in:

- **Name**: what it's called in Sugabots.
- **Address**: the server's URL. Sugabots connects to remote servers over
  Streamable HTTP. It doesn't run servers itself.
- **Sign in with**: how Sugabots proves itself to the server.
  - **Token**: an access token, sent as `Authorization: Bearer <token>`. Leave
    it empty if the server needs none.
  - **Sign in**: the server's own sign-in, which you complete next.
  - **Header**: a secret sent exactly as typed, in the header you name.
- **Approval**: **Ask** or **Allow**. New connections start on Ask. Once it's
  added, you can also set it to **Off**.

## Look after it

A connection's page shows whether it's signed in, and **Check connection** asks
the server which tools it offers right now. Tools are named after the
connection, like `linear__list_issues`, so bots can tell apps apart.

If a server can't be reached, its tools are left out of that turn and the bot
carries on without them.

<Careful title="Removing a connection">

Bots in the pod lose its tools straight away. Adding it again means signing in
or entering its details again.

</Careful>

## Troubleshooting

### Check the server yourself

Ask the server for its tools from the machine that runs Sugabots, with the
credential the connection sends. This takes Sugabots out of the picture:

```sh
curl -i https://mcp.example.com/mcp \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
```

A working server answers `200` with JSON describing itself. If `curl` fails
the same way, the problem is in the server, its address or the credential, not
in Sugabots. The full error behind each message is in Sugabots' logs:
`docker compose logs sugabots`.

### The token or secret isn't accepted

- Most servers want the `Authorization` header to be `Bearer` followed by the
  token, such as `Bearer abc123`, not the token on its own.
- Tokens are often tied to the account that made them, so they can only reach
  what that account can. Some expire, and some are revoked when the account's
  password changes.
- Copying a token from a terminal or email can add a line break or drop a
  character. Paste it into a plain text editor first to check.

### The server refuses access

The credential was accepted but lacks permission, an `HTTP 403`. Check the
token's scopes or the account's role on the server. Some servers also refuse
requests from addresses they don't recognise, so check any allow list the
server has.

### Nothing answers as an MCP server

- Sugabots speaks MCP over Streamable HTTP. A server that only offers the older
  SSE transport, often at an address ending in `/sse`, won't answer.
- The MCP address is usually on a path such as `/mcp` or `/api/mcp`, not the
  server's home page. The server's documentation lists it.
- A reverse proxy in front of the server can answer with its own page. Check the
  proxy forwards the MCP path.

### The server can't be reached

- When Sugabots runs in Docker, `localhost` and `127.0.0.1` mean the Sugabots
  container itself. Use the server's network address, such as
  `http://192.168.1.20/mcp`, instead.
- Check a firewall on the server, or between the two machines, allows the port.
- Sugabots gives up after 15 seconds, so a server that is slow to start may need
  a second check.

### Sign-in won't start

Sugabots signs in to a server by registering itself with the server's sign-in
service first, which the OAuth standard calls dynamic client registration. Some
servers only accept apps registered another way, so their sign-in can't be used
yet. Connect with an access token from the server instead.

### The address isn't allowed

By default, an installation only connects to `https://` addresses on the public
internet, so that one workspace can't reach other services on the network or
send keys unencrypted. Whoever runs Sugabots can allow plain HTTP and local
network addresses with the [network settings](/docs/configuration#network).
